Experiments: finding where project memory helps

21 October 2026 · Antony Clements

I’m adding an Experiments section to document a question at the heart of Augmented Workflow: does giving an agent persistent project memory make it more effective, with less guidance and correction from the people working with it?

AW is built around preserving the knowledge that accumulates as a project develops. That includes decisions and their rationale, specifications, coding standards, a context wiki, session logs and lessons from previous work. The expectation is that an agent joining the project can use that knowledge instead of requiring someone to reconstruct it each time.

It is a reasonable expectation, but it needs testing. Reading and maintaining those records takes effort, and some of the information may already be clear from the code and tests. I want to understand where the memory layer provides a net benefit, where it adds unnecessary work, and what needs to change when it falls short.

The handoff problem

The underlying problem is familiar to anyone who has joined an existing project. The current implementation tells you a great deal about what the system does, but it may leave you guessing about why a decision was made, which alternatives were rejected or what remains unfinished.

A human colleague benefits from a handover that explains those things. An agent should have access to the same kind of useful context. Knowing that an endpoint is implemented but the interface is not connected, or that targeted checks passed while the browser flow remains untested, gives either one a better starting point than “mostly done.”

The benefit could extend beyond a single handover. A decision made during product design may matter later to engineering, support or marketing. A coding standard may need to survive several changes of agent. A session log may preserve the reason an apparently obvious approach was abandoned.

Those are the situations I want to investigate, rather than assuming that more documentation always improves the work.

What we are comparing

The central comparison is between a project with an accumulated memory layer and the same project without one. Both retain their code, tests and ordinary implementation comments. Both can ask a helpful stakeholder questions. The difference is whether established knowledge can also survive in maintained project records between sessions.

Getting that distinction right took some work. Early comparisons gave both conditions access to the same history in different formats, which tested ways of organizing memory rather than the value of having a memory layer at all.

A fair control should remain a capable agent with useful tools and access to answers. Removing helpful code or making the stakeholder deliberately uncooperative would manufacture an advantage for AW. Equally, memory should develop through the work rather than arrive as an answer sheet containing future requirements.

The broader aim is to test the philosophy behind AW. Specific features and formats can be evaluated separately once there is evidence about which kinds of continuity are worth supporting.

What the first pilots suggest

The first pilots have already produced different outcomes.

In a small billing project, fresh agents implemented order quotes, added batch quoting and then added refunds. The agents with memory and those without it passed the same acceptance checks on their first submissions. They asked the same number of stakeholder questions, repeated none and needed no corrections. Existing code and tests provided enough continuity for the later work, while memory added reading and maintenance. There was no measured guidance or correction benefit in that sequence.

A second pilot explored a simulated handoff from product/design to engineering and then support-related work. An initial session established privacy requirements for a shared-device project. Later work needed parts of that policy that were not fully expressed in the existing interface code.

Across the two matched project pairs, agents without the memory layer requested four repeated explanations, compared with one for agents with memory. Both conditions still passed every session’s acceptance checks on the first submission, without correction rounds. The observed difference was less repeated guidance, not better accepted code.

There was a cost: the memory condition read more text and performed more recorded actions, including updating its notes. The stakeholder was scripted, so these requests did not interrupt a real person. We did not measure human time, token usage or financial cost, and the result does not establish a net productivity gain.

These are small synthetic pilots with simulated roles, concise recent knowledge and only two matched project pairs in each study. They test AW-style memory, not a full AW installation or a real cross-functional team. They also bundle several kinds of knowledge together, so they cannot tell us whether a particular standard, decision record or session log deserves the credit.

What belongs in the evidence

The individual experiment write-ups will cover the tasks, comparison conditions, checks, results and limitations in enough detail to make the conclusions inspectable. This introduction sets out the questions those studies should answer.

Correctness matters, but so do repeated explanations, correction rounds and the effort required to recover context. Any claim about efficiency must also account for the work of creating, finding and maintaining the records. A smaller number of questions is useful evidence only when we understand what replaced them.

Negative findings belong alongside positive ones. If code and tests are sufficient, that helps identify where extra memory may be unnecessary. If stale notes mislead an agent, or a context wiki becomes too costly to navigate, that should lead to a documented change and another test. The same scrutiny applies when an experiment itself turns out to ask the wrong question.

Where to look next

I’m particularly interested in coding standards applied across features, context wikis that explain unfamiliar parts of a project, session logs that preserve unfinished work, and decisions that need to travel between functions. Cross-functional handoffs may be especially revealing because the next person or agent often needs knowledge that the previous implementation does not express.

Those tests also need less favorable cases: conflicting records, changing requirements, older decisions and tasks where the code already provides everything necessary.

Over time, this section should build a body of evidence about where persistent project memory earns its upkeep. When it helps, I want to understand why. When it does not, I want the result to improve AW and our understanding of when to use it.

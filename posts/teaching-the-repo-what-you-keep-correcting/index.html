Teaching the repo what you keep correcting

11 October 2026 · Antony Clements

The same correction again

“I think you’re looking at an older version?”

There’s a learning in Augmented Workflow with that correction in it. An agent had delivered an evaluation against a version of the repo with roughly thirty-three skills. The repo had already been consolidated to twenty, and a field guide had been added. The evaluation was confidently describing something that was no longer there.

The immediate repair is straightforward: read the current files and do the evaluation again. The more interesting question is what happens next time.

A correction costs attention. Someone has to notice the mistake, work out what assumption produced it, and explain the difference. If that explanation disappears at the end of the conversation, the next session can make the same mistake for the same reason. The repo changes; the supervision starts over.

Writing the correction down seems an obvious answer. But there are several ways to write this one down, and some would leave the next agent worse off.

What should survive

“There are twenty skills” would have been accurate at the time. Put it into permanent guidance and it becomes another stale fact waiting to mislead someone.

“Check the current repo before evaluating its structure” survives a change in the number. It also tells the agent where to get an answer when the remembered one is wrong.

The recorded lesson goes further. It explains that skills consolidate, files move and registries change. It names the situations where a fresh look matters: evaluations, reviews for drift, and returning after the branch may have moved. It gives a small action to take before drawing conclusions: inspect recent commits, list the relevant directories and reread the files.

That’s enough to change how the next evaluation starts. It preserves the reason the correction was needed.

This is where I’d start with any repeated correction. What assumption made the wrong approach seem reasonable? What would have exposed that assumption before the work went ahead?

The answer may be a check, a missing constraint or a decision somebody already made. “Be more careful” won’t help much. The next agent needs something it can actually do.

Where it applies

A correction also needs a boundary.

Suppose I ask an agent to leave an old API alone while changing a particular screen. There might be a migration in progress, another team depending on that API, or simply no reason to expand this job. Save “never change the old API” and a temporary constraint can become a permanent obstruction.

A useful record would say which work it applied to and why. When the migration finishes, someone should be able to recognise that the reason has gone.

AW’s capture guidance separates repo-specific lessons from preferences intended to apply across repositories. It asks before making a lesson global, and skips ordinary clarifications and preferences explicitly described as temporary.

Those boundaries matter. A choice that was sensible in one codebase can be wrong in another. Even within one repo, the conditions can change.

There’s a practical check here: could another engineer read the lesson and tell when to ignore it? If every sentence sounds like an instruction for all future work, it probably needs another pass.

How a note acquires authority

Once a lesson is written down, it starts to look established. Give it a title, put it in an index, load it at the start of a session, and the next agent has a reason to follow it.

That can preserve a misunderstanding just as efficiently as a useful correction.

In AW’s synthesis guidance, a new single-session learning starts as tentative. Corroboration across three sessions makes it active. Tentative entries are removed after three consecutive synthesis runs without corroboration. Turning a recurring pattern into a project standard requires human confirmation.

The immediate correction still applies to the work at hand. The threshold concerns how much weight a stored generalisation should carry in later sessions.

These are practical rules for managing the notes. Three sessions aren’t a demonstrated threshold for truth, and three quiet runs don’t establish that a lesson was wrong.

The distinction matters because repeated records can share a mistake. Three sessions may all have inherited the same bad instruction. An agent may describe a previous claim as something it has confirmed when it has only read it again.

The stale-repo learning lists three source sessions. That gives me an audit trail to investigate. The count alone doesn’t show three independent tests, or establish that later evaluations improved.

I still need to look at what happened in those sessions. Did the situation genuinely recur? Was the assumption checked against the repo? Did following the lesson help? A status field can organise that work, but it can’t answer those questions for me.

Memory needs maintenance too

There’s an awkward consequence of all this: the notes themselves become something to review.

A lesson can be right when captured and wrong six months later. It can have an accurate explanation and an instruction that no longer follows from it. Two lessons can each make sense alone and conflict when they’re loaded together.

Keeping the source and the reason gives someone a chance to resolve that. Without them, the instruction has to be accepted on trust or discarded on instinct.

For the repo-state example, the note should send the agent back to current evidence. If a later summary turns it into a fixed description of the repo, the summary has lost the useful part.

I’d also want a changed lesson to replace or clearly supersede the old one. Appending a correction somewhere else leaves the next reader to discover that there are two answers and work out which came last.

All of this costs something. A growing collection of instructions consumes context and reading time. Capturing every minor adjustment would create another pile of material that somebody ought to review and probably won’t.

Did the next session improve?

The easiest thing to count is the number of learning files. It tells me very little about whether this is working.

For the stale-repo correction, I’d want to see a later evaluation inspect the current tree before describing it. Better still, check what happens after the structure changes again. Does the agent find the new shape, or faithfully repeat the last saved count?

I’d also look for fewer repeated corrections when comparable work comes around. Silence by itself is weak evidence: perhaps nobody checked, or the relevant situation never arose. The useful observation is that the agent reached the point where it previously went wrong and handled it properly.

In Code Without a Theory, I wrote about keeping the reasons behind decisions available. In Did you wash your hands?, I wrote about asking what the evidence actually establishes. A learning record needs both.

The aim is for the next session to benefit from attention already spent, while leaving room to discover that the old advice no longer fits.

A good place to start is the correction you’re tired of making. Write down what caused it, where the lesson applies and what the next agent should check. Then watch what happens when it gets another chance to make the same mistake.

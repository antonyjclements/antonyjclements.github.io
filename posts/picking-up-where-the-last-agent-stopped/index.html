Picking up where the last agent stopped

19 OCT 20267 MIN READANTONY CLEMENTS

If you were handing an unfinished feature to a colleague, you probably wouldn’t point them at a branch and say “carry on”. You would explain what you were trying to achieve, where you had got to, and anything they should know before changing it.

A fresh agent session faces much the same handover problem. It can inspect the files, but that does not tell it which approach was agreed, which alternative was rejected, or whether the passing tests cover the part you were worried about. Without that context, it may continue on a different basis.

In Code Without a Theory, I wrote about the understanding behind a program and how much of it is missing from the code itself. We recognise that gap when one person takes over from another, and I think it is a useful place to start when deciding what an agent needs.

My last article looked at corrections that should survive beyond a conversation. Here I want to look at the unfinished work itself: what would make a handover useful to whoever picks it up next?

What “carry on” leaves out.

Suppose we are adding a CSV export to a reporting screen. This is a hypothetical example, but the handover should be familiar to anyone who has taken over a partly finished feature.

The requirement is to export every matching record using the filters selected in the UI, while the screen and its reporting API are paginated. Generating a CSV from the rows already loaded in the browser would give us a file that looks correct but contains only part of the result.

Suppose the first session catches this, chooses a server-side export and adds the endpoint, but stops before the button is connected. A colleague looking at the branch might work out why the endpoint exists, although we would save them some investigation by explaining the decision.

“CSV export mostly done” leaves either a person or an agent to decide what mostly means. I would find a checkpoint like this more useful:

SAVE POINT · CSV EXPORT

  • The export must include all matching records, not just the visible page.
  • The endpoint is implemented; the UI is not connected.
  • Browser-side generation was rejected because the UI only holds one page of results.
  • The targeted endpoint checks passed at the recorded revision. The full suite and browser flow have not been checked.
  • Next: connect the button to the endpoint, then verify an export containing more than one page of results.

There is nothing specifically agentic about that list. It would be an equally useful human-to-human handover because it explains the requirement, the state of the work, the reason for the approach and what still needs checking. In a real checkpoint, I would include the relevant file paths, revision, test commands and results so the recipient can follow them up.

A colleague could reasonably suggest generating the CSV in the browser if they did not know about the pagination constraint, just as another agent could. Recording the reason lets either of them assess the decision without having to rediscover it.

A checkpoint and a project memory.

In a team, I would expect a handover note and the project documentation to answer different questions. The handover tells the next person what they are taking on; the specification and decision records explain the behaviour we are trying to build.

The export’s unfinished button belongs in the handover, while the requirement to include every matching record should still be easy to find long after the button is connected. Keeping those separate avoids turning temporary task instructions into permanent project guidance.

In Augmented Workflow, the workstream checkpoint lives in a local, git-ignored progress file. The agent is instructed to maintain that record and reconcile it with the checkout when resuming; it is not an automatic restore of a previous session. Session logs and the generated context wiki provide the broader project context.

The local file has a practical limitation: it will not follow a clone onto another machine. If the work is moving elsewhere, the checkpoint has to be transferred deliberately and checked against the destination. A handover saved only on someone’s laptop is of little use to a colleague working somewhere else, and the same applies here.

Helping someone find their way around.

A colleague joining a project needs somewhere to start without reading its entire history. AW’s memory-synthesis workflow serves a similar purpose for agents: it reads session logs, extracts useful corrections, dead ends and recurring patterns, and regenerates a short project context wiki from the available material.

This depends on those logs being captured in the first place. Hooks are optional, so ending a conversation does not guarantee that a record of it exists.

The wiki is kept under 500 words and points towards active features, recent decisions, learnings and known dead ends. It is an optional starting point rather than context every session is guaranteed to receive, and its brevity makes the underlying records important.

For the export, the checkpoint tells the next session where to connect the button, while the feature specification and decision record explain what the export must contain and why the server-side approach was chosen. The wiki helps the agent find those records.

I would not expect an overview written for a person to preserve every qualification from the original discussion, and an agent-generated summary has the same problem. If a detail affects correctness, it needs to be recorded in the specification or decision itself rather than left for the summary to carry.

AW regenerates the wiki rather than maintaining it through hand edits, and its links should point to durable repository artifacts instead of session-log paths that retention may later remove. That keeps the overview connected to records someone can still inspect when they need more than the summary.

Read the handoff, then check the checkout.

Taking over from a colleague does not remove the need to look at the current state of the work. Their handover might have been accurate when they wrote it, but the branch could have moved or someone else could have changed the endpoint since then.

For an agent, I would make that check an explicit part of resuming: read the checkpoint, inspect the branch and working changes, then compare the relevant files with what the note describes. A test result from the previous session tells us what passed then, not necessarily what passes now.

The handover should make this investigation smaller. In the export example, it identifies the decision worth checking, the unfinished UI work and a useful verification step: comparing the exported records with the complete filtered result, rather than just the visible page.

It also needs to distinguish an agreed decision from an open question. If a colleague wrote “we discussed limiting exports to 10,000 rows”, I would want to know whether that limit had been agreed before implementing it. An agent needs the same distinction made clear rather than treating mention of an option as permission to choose it.

People can ask the person handing over, draw on earlier conversations and recognise who owns a decision. A fresh agent session may lack that background, so I would be more explicit about unresolved questions and when it should come back to a person for an answer.

Would this be enough to take over?.

Handing a colleague the entire chat history would technically give them more information, but it would also leave them to work out which parts still apply. Saving every tool response and plan revision creates a similar burden for the next agent. The useful work is deciding what the recipient needs to know and where they should look for the rest.

A written handover can still omit a reason or describe a decision badly, and its existence does not tell us whether the recipient has understood it. I would test this one by asking a fresh session to explain what remains unfinished, why the export is server-side and what it would verify before calling the feature complete.

If it proposes exporting the visible rows, or assumes that the browser flow has already been tested, there is something to revisit in the handover or how it was used. Those are the same misunderstandings I would want to catch while talking the work through with a colleague.

That is the standard I would use when closing an unfinished agent session: leave the kind of handover I would want from another developer, with enough explanation to continue the work and enough honesty about what is still unknown. The next session should not have to reconstruct a conversation we could have summarised properly before leaving.

When the guardrails need tests

5 NOV 20266 MIN READANTONY CLEMENTS

In Did you wash your hands?, I wrote about using deterministic checks to answer narrow questions about an agent's work. A script can tell me that a required record is missing or a reference is broken, leaving more attention for the decisions that need judgement. That depends, of course, on the script answering its question correctly.

A recent experiment found a fairly ordinary bug in one of Augmented Workflow's checks. A missing document could pass validation, while an existing document could be rejected. Both failures came from the way the checker read a comment in an index file.

The fix has now shipped to the project's main branch. The part worth explaining is how the tests exposed the problem, particularly why an apparently successful check had been giving us less evidence than it seemed.

A small question about a file

AW keeps indexes that help an agent find specifications, decisions and other project records. An index is useful only if the references it contains lead somewhere, so one of the checks looks for documentation paths and verifies that their targets exist.

This is a modest requirement. Finding a decision record does not establish that the decision is current, well explained or appropriate for the work. It does let us catch a broken reference before someone follows it while trying to understand the project.

The index uses a limited YAML format, with fields such as path and spec. Someone maintaining it might put quotes around a filename or add a comment after it. Neither should change which file is being referenced.

Here is the kind of field that exposed the missed check:

path: "docs/decisions/absent.md" # still missing

In the test repository, that file did not exist. The original checker nevertheless accepted the index.

Two ways to get the wrong answer

The parser tried to remove enclosing quotes before dealing with the trailing comment. Because the whole value ended with the comment rather than a closing quote, it left the leading quote in place. The next stage only checked values beginning with docs/, so this value was skipped without testing whether its target existed. The relevant parser and existence check make that sequence visible.

A quoted path with a comment also passed when its target did exist. Looking at that result alone, I could have concluded that the format worked. Pairing it with a missing target showed why that conclusion would have been wrong: both received the same answer because neither reached the existence check.

There was a failure in the other direction too:

path: docs/decisions/note#1.md # reviewed

Here, note#1.md was a real file. The hash in its name was part of the filename, while the later hash introduced a comment. The parser retained the trailing comment as part of the path, looked for the wrong filename and rejected a valid index.

These two cases matter together. Testing only missing files would tell us whether the check could stop some broken references. Testing only existing files could miss a check that quietly skipped them. A useful validator has to distinguish the two, including when the input is written in an ordinary variation of the supported format.

Testing the check itself

The supplemental experiment set out six reserved cases and their expected answers before developing the candidate fix, then froze the candidate before running those cases. They included existing and missing targets, quoted values, literal hashes, a plain path and a malformed list entry. The original source and candidate were run against the same examples, with both sets of results retained.

The original accepted three of the four valid cases and rejected one of the two invalid cases. The candidate classified all six correctly. That is enough to demonstrate the two specific failures and their correction on those inputs, although six related examples leave plenty of possible parser behaviour untested.

The expected answers also needed checking independently of AW. A later review used a separate YAML parser and inspected the fixture files and saved results. That review was retrospective; it did not independently rerun the reserved cases or regression suites. Keeping that distinction visible matters when describing how much confidence the evidence supports.

For the merged change, the regression tests cover a wider set of combinations. Both reference fields are tested at the start of an entry and as continuation fields, with bare, single-quoted and double-quoted values, including literal hashes. Each form is checked with its target present and absent. Another case checks that a commented specification reference remains discoverable through the feature index.

That adds 49 regression cases. For missing targets, they also check the reported filename, which helps establish that the failure came from the intended condition rather than an unrelated error.

What shipped

The merged change removes an inline comment before stripping enclosing quotes, using the existing quote-aware helper. It updates both the source distributed by the installer and the copy AW uses in its own repository. The correction is available on main at commit 9d99efac.

The shipping validation passed all 65 derived-state cases, the 162-case gate suite and the original six reserved cases. Two broader checks still failed in the same way on unchanged main: an installation check expected 20 bundled skills where there were 21, and a behaviour check expected tracing to be disabled despite the current configuration enabling it. Those failures are recorded in the pull request rather than hidden behind a claim that everything passed.

This is a correction on main, without a new tagged release or an automatic update to existing installations. The parser still supports a deliberately narrow index format; the change does not establish general YAML compatibility.

A fix is a different result from an agent benefit

The wider experiment also compared automatic enforcement with voluntary checking. There were eight agent runs, arranged as four matched pairs across two small task families. Both groups had the same project information, tools and constraints, and both could run the checks themselves. The difference was whether a check also ran automatically at submission.

All eight agents voluntarily checked their work and passed every measured component at the first and final endpoints. There were four paired ties, with no invalid submission for automatic enforcement to stop. Those small, strongly cued tasks gave us no observed correctness advantage from enforcement, and they tell us little about its value in a real team.

Finding a bug in the checker does not change that result. It gives us a concrete improvement to make while the broader effectiveness question remains open, which is one of the reasons I wanted to run these experiments in the first place.

For this check, the most useful test was the pairing: a reference to a file that exists and the same supported form pointing to one that does not. It made the meaning of a pass much clearer. I still have to read the document and decide whether it helps explain the project, but I can now have better-founded confidence in the narrower answer the script was supposed to give me.

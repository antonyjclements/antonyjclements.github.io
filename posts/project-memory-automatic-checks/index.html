AW-DUAL-003 · EXPERIMENT REPORT

Project memory, automatic checks and the work worth measuring

10 NOV 202610 MIN READANTONY CLEMENTS

I’m testing two ideas behind Augmented Workflow: that accumulated project memory can help a fresh agent recover established knowledge, and that automatic checks can help enforce a project’s workflow requirements.

The latest experiment found a narrow benefit from memory. Agents with an accumulated archive received fewer repeated explanations while reaching the same measured correctness as agents without one. Automatic enforcement produced no correctness advantage in its separate comparison.

The memory agents also performed more recorded operations. That deserves careful interpretation. Reading and updating their records was automatic. A higher operation count does not tell us that a person had more work to do, or that the workflow was less efficient overall.

The useful question is whether automatic work improves the outcome, reduces the attention people need to give it, or creates costs that matter in practice. This experiment measures some parts of that question. It leaves others open.

Two comparisons, kept separate

The memory track compared two matched pairs of projects. Each project passed through three fresh agents in simulated billing, data integration and support roles. Both conditions began with the same implementation, tests and ordinary README. Both retained their evolving code, tests and normal implementation comments.

The memory condition also built an archive through the work: standards, context, decisions, specifications, session logs and lessons. It began empty. The control received no substitute archive of earlier conversations or decisions.

Both conditions could ask the same helpful simulated stakeholder for information. This time, the available topic names were explicit, so agents could ask for selected topics or request a broader explanation. That addressed an ambiguity in the preceding experiment without making the control less capable.

The sequence involved invoices, refunds, then support exports and a dashboard. The final request explicitly changed an earlier eligibility policy, from a creation-time cutoff to an inclusive service-start cutoff. That let us examine whether the agents could follow a new decision rather than preserve an old one simply because it was recorded. Existing summary behavior also provided a case where code alone could supply continuity.

The enforcement track used a different task and four fresh agents, arranged in two matched pairs. They repaired quota admission while preserving tenant isolation, remaining capacity and an audit event. Both conditions could run optional workflow checks. Only the requirement to pass an automatic check at submission differed.

These are separate experiments. They do not measure a combined effect of memory and enforcement, or an interaction between the two.

Memory reduced repeated explanation content

Both memory conditions passed every measured session outcome on their first and final submissions: six out of six per condition at each point. Across the two conditions, all 24 saved first/final revisions passed the reserved checks.

Neither condition needed a failure-driven correction. Neither changed application code or tests after its first submission. Every session received the same scheduled reminder regardless of whether its work was already correct. Those reminders were part of the protocol, rather than evidence that an agent needed help.

The difference appeared in what the agents asked to have explained:

  • Both conditions made six stakeholder calls.
  • Agents with memory received 16 topic explanations, compared with 26 without memory.
  • Four explanations repeated a topic-answer pair from an earlier session in the memory condition, compared with 14 in the control.

The direction was consistent across both project pairs, although its size varied. Repeated explanations were four versus seven in the first pair, and zero versus seven in the second.

Both agents working on refunds with memory requested only the new refund topic. In the final stage, one memory agent requested all topics, while the other requested only the current cutoff and support topics.

That is a useful, specific result: accumulated records helped reduce how much established information was requested again. They did not reduce the number of contacts with the stakeholder, and they did not improve correctness on these tasks. Both conditions also handled the explicit policy change successfully.

What the extra automatic operations mean

The memory condition recorded 145 operations, compared with 67 without memory. Of those, 69 were archive operations: 24 reads and 45 writes. Both conditions made 16 application or test writes. The memory agents ran ordinary tests ten times, compared with six in the control; all passed.

It would be misleading to turn those totals into a claim that memory made the user do more work. The agents maintained the archive themselves.

The count also gives every recorded operation equal weight. A note read, a test run and a stakeholder request each contribute one operation, despite potentially very different consequences. The totals describe activity. They are not a weighted measure of effort or cost.

If automatic record-keeping saves a person from reconstructing a decision, the extra machine activity may be a good trade. It could also consume model context, tokens, elapsed time or infrastructure resources. Which effect matters depends on the actual workflow and what those resources cost.

This study did not measure that trade. Its stakeholder was a scripted tool, so the reduction in repeated explanations did not save any observed human minutes. Question counts were unchanged. Model token usage, billing and end-to-end working time were unavailable; recorded tool execution durations exclude model thinking and do not establish a speed advantage or penalty.

Automatic upkeep is therefore something to account for when evaluating the system, rather than an automatic argument against memory. The supported result is fewer repeated explanations at equal measured correctness, with more automated activity. Whether that is a net benefit remains an empirical question.

The enforcement comparison also tied on correctness

All four enforcement-track agents passed every measured first/final outcome. Both conditions therefore finished two out of two projects successfully, covering functional behavior, registry and specification requirements, review of the current source, configured routing and simulated permissions.

Every first submission was accepted. There were no stakeholder questions, owner corrections or post-submission edits.

This track deliberately used an older AW revision containing a previously reproduced parser problem. A valid registry could contain a literal hash in a filename followed by an ownership comment. The legacy checker could misread that valid entry and report a failure.

All four agents chose to run optional checks. Both agents in the automatic-enforcement condition encountered the legacy false block, reformatted the registry, obtained another review and checked again before submitting. One control agent reformatted proactively. The other retained the valid registry, accurately reported the check failure and submitted correct work.

Across the experiment, three optional checks falsely blocked valid work. Zero automatic submission checks did so. Both automatic submission checks ran after the agents had already made their formatting changes and accepted the work.

This distinction matters. The experiment observed needless work around a legacy optional check. It did not observe automatic submission enforcement rejecting valid work or rescuing an otherwise incorrect submission.

The enabled condition recorded 40 operations, compared with 35 in the disabled condition, and obtained four reviews rather than two. Those differences cannot establish that automatic enforcement caused extra repair work: the differing choices happened before the enforcement-specific submission action. With only two project pairs, descriptive differences in agent behavior should not be promoted into causal conclusions.

Reviews were issued by a configured simulated provider after smoke tests, not by human reviewers. Permission-related external effects were also simulated locally.

The parser defect is already fixed in the captured current code

The legacy behavior is useful for understanding a failure mechanism, but it would be wrong to describe it as an unresolved defect in the current version inspected for this study.

Four reserved compatibility cases covered valid and missing files using bare and quoted paths with ownership comments. The original parser falsely blocked the valid bare hash path and failed to detect the missing quoted path.

Both the previously developed isolated fix and the captured current-main gate correctly accepted the two valid cases and rejected the two invalid ones. Neither was tuned after seeing these reserved results.

The legacy actor trials used revision 4266982a4c045aaa9365a1195f0f79cffc7552a4. The captured current main was 9809583218683528be6e56ce56058c40412987fa.

That is evidence that the captured current code handles these four cases. It is not a full current-version evaluation: there were no fresh-agent causal trials on that version, and the focused regression checks were not a full CI run.

The static checks also repeated earlier coverage probes. Several stronger-policy expectations remained outside the documented gate contract or used documented escape hatches. Those results should not be relabeled as newly discovered defects.

How much confidence should we place in this?

These are small synthetic studies. The memory track has two paired project trajectories, with sessions nested inside them. Twelve sessions are not twelve independent projects. The enforcement track has four actors. Neither comparison supports a statistical significance claim or a conclusion about real human teams.

The memory study is a replication within an existing task family, not a test of generalization to a new domain. It evaluates accumulated project memory as a bundled approach, including required upkeep across six categories, rather than identifying which category helps or testing a full AW runtime integration.

Plans, inputs and executable scoring were frozen before the actors began. Independent development validation accepted three valid memory references and rejected 29 deliberate mutations; the enforcement validator passed 38 assertions. Reserved memory scoring waited until every actor had finished. Failed checks and all assigned outcomes were retained, with no poorly performing trial replaced or excluded.

The audit trail has two qualifications worth stating plainly. A deterministic-track audit document received an addendum after hashing; the original manifest and disclosed exception remain intact, and the frozen experimental inputs did not change. The memory validator’s substantive verdict preceded the freeze and actors, but its full written report arrived just after the freeze and was not in that manifest. These are local hashes and timestamps, not an external preregistration service.

Two memory first-submission claims also used the wrong reporting structure. They remain recorded as formatting defects. Their raw assertions were separately checked against passing tests and acceptance at the same revision; they were not silently converted into conforming claims or removed from the results.

The comparisons used matched default model selection, tools and budgets, but exact backend builds and sampling seeds were unavailable. Isolation between projects was procedural rather than a security sandbox. Instrumented logs preserve the observed operations and payloads, but cannot prove the absence of every possible uninstrumented action.

These limits leave a useful observation, provided we keep its scope intact.

What this adds to the AW evidence

Earlier pilots include comparisons that asked the wrong question, a small billing sequence where memory offered no measured benefit, and a cross-role example where it reduced repeated guidance. Those results remain part of the picture.

This replication adds another narrow result: memory reduced repeated explanation content while correctness and question counts stayed the same. It also shows why counting automatic operations as if they were human effort would obscure the question we actually care about.

For enforcement, the result is another correctness tie, evidence of a known legacy parser problem during optional checking, and confirmation that the captured current fix passes the reserved compatibility cases. It does not establish broad present-day benefit or harm from automatic enforcement.

The next useful evaluation would connect these observations to outcomes that matter in practice: how much attention people need to give the work, total time to an acceptable result, resource cost, and whether the benefit survives longer projects and changing decisions.

My aim is to understand where AW makes agent-assisted work easier and more dependable. More automatic activity may be entirely worthwhile. These experiments help identify what that activity achieves, and what still needs measuring before we can say how much it is worth.

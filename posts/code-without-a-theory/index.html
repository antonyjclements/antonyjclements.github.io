TRANSMISSION_001 / AI & ENGINEERING

Code Without a Theory

July 2026 · Antony Clements

Twenty approvals

File write? Yes. Bash script? Yes. File write? Yes. Install a dependency? Yes. Yes. Yes.

Somewhere in that run, the agent set up a local file-based data store. I’d expected DynamoDB. It never asked me about that one. It asked about everything else, so I was busy clicking through file writes and shell commands while the one decision that changed the shape of the system went through without a prompt. I found it later, reading a file while I was chasing a different bug. I was lucky.

In fairness to the agent, it didn’t do anything obviously wrong. It needed to store some data, and the codebase gave it two examples: some parts wrote to a DynamoDB table, others read a JSON file off disk. It had evidence for both and picked one. What it didn’t have was any idea which of those belonged to the system it was working on. Someone who’d held that codebase in their head would have had a reason to rule the file option out. The agent never got that reason.

The agent had none of that background, and I don’t think a bigger model fixes that on its own.

Naur

In 1985, Peter Naur wrote a short paper called Programming as Theory Building. His argument is that programming isn’t mainly about producing code. The real work is building a theory in the heads of the people doing it: an understanding of the problem, of the program, and of why the code has the shape it has. The code is what’s left over.

Someone who holds that theory can do more than make changes. They can explain the changes, justify them, and answer questions about why the thing works the way it does.

Then he makes the claim that matters here. In his account, the theory can’t be fully written down. He isn’t just saying people are bad at documentation. He argues that reviving a program from its documentation alone is “strictly impossible.” Docs still matter, but they can’t stand in for the people. When the team that held the theory breaks up, Naur calls the program dead.

It helps to separate two things that get lumped together. You can nearly always work out what a system does. Read it, run it, trace it, and the behavior gives itself up. What you can’t reliably recover from the code alone is why it does it that way: the option somebody rejected, the constraint that made this design feel obvious. Some of that may never have made it into the code. It was in the people who wrote it.

A dead program still runs. It can be useful and pass its tests. You find out it’s dead the first time someone asks for a change and nobody can say what will break, or whether an odd line was deliberate or just drift.

If you can’t recover the theory from code, checking code you’ve been handed is expensive. If you can’t fully write the theory down before you build, whatever you build will miss some of what you meant. Those are the two problems I keep running into with agents, and they pull in opposite directions.

Reading code is still slow

Careful review can mean a few hundred lines an hour, depending on the code and the kind of review. SmartBear’s guidance recommends staying below 500 lines an hour. It isn’t a universal speed limit, but it gives a sense of the scale. Building a model of what a change does, checking it against what it should do, then checking it against the rest of the system takes time. It always has.

The writing side is what changed. Four hundred lines used to cost an afternoon. An agent now produces them in about the time it takes to read this sentence.

So the ratio has flipped. Writing used to be the expensive part and review was the tail. Now writing costs almost nothing and review is where the time goes, and most of us are still running a review process built for the old volume at several times that volume.

That’s the easy half. Naur explains the harder half.

When you write code yourself, you have to make decisions as you go. That doesn’t guarantee you understand the whole system. But by the time a diff exists, you’ve had a chance to build an understanding of why it looks like that, because you made it look like that.

When an agent writes it, you can get the code without going through that process. If nobody stays close enough to the decisions, review becomes an attempt to build an understanding that no accountable person has yet developed.

I don’t want to overstate this. Agent output isn’t random. It carries your prompt, the examples you showed it, whatever local context it read, and everything it picked up in training. There are scraps of theory in there. A supervising engineer can still hold the system-level understanding and answer questions about it. The risk is that the workflow lets implementation move ahead without anyone doing that work. Code review often quietly relies on someone having done it.

Naur’s dead program had a team once, and the team left. Agent code can show up already in that state on day one: it runs, it’s useful, and nobody accountable understands it well enough to change it confidently. When that happens, code reviews cost twice over. There’s more of it, and it’s harder to check because the reviewer has to build the missing understanding too.

The ratchet

The usual advice is discipline. Read diffs properly, slow down, build the theory yourself. I don’t think discipline is the main problem here. The problem is money and time.

I started using agents because they’re fast. If checking their work costs as much as writing it used to, the speed-up is gone. The person who checks everything doesn’t get the productivity they were promised. The person who doesn’t check ships code nobody verified. The incentives reward skimming, and you can’t fix incentives with a memo.

It also gets worse over time. I read a diff carefully and it’s fine. I read the next one carefully, also fine. By the tenth, careful reading feels like wasted effort, because a quick skim would have got me to the same place. So I skim, and it’s fine, and I skim a bit more.

Weeks later, a bug turns up in production. I trace it to a PR with my name on it, one I know I skimmed. I overcorrect and spend three days reading everything properly. Then the next ten diffs are fine and I drift back.

The punishment is real, but it arrives rarely and late. The reward for skimming arrives every single time. None of the individual decisions feels reckless while I’m making it.

Better models speed this up. The more often the code is right, the more evidence I collect that careful review was unnecessary, and the sooner I stop doing it. The mistakes that get through become rarer and more convincing, because they’re the ones that look right. My attention drops just as the cost of missing something goes up.

That’s what worries me most. The code often isn’t bad. It’s that judging it gets harder as the models get better.

Weren’t reviews already bad?

You could argue none of this is new. People were approving PRs with “LGTM” long before agents turned up.

That’s true. But shallow human review often had something underneath it: an author who could explain the work. That never meant they shipped no bugs or understood everything. It meant that when production broke, there was someone to ask what the code assumed, what it touched, and why it was built that way.

Agent-written code can have that person too, if someone has stayed involved enough to understand it. Take away that understanding and the shallow review is all that’s left, with nothing under it.

Lazy review was always there. Agents make it easier to produce working code without anyone building the understanding that used to help cover for it.

The usual fixes, and where they run out

Take a simple spec: orders over £100 get 10% off. I meant £100 before tax. The agent read it as including tax and built it that way.

“Get the agent to review its own code.” The agent still believes the threshold includes tax. That belief is the bug, and re-reading its own code won’t shake it. It’s like proofreading when you’re sure “definately” is spelled right. You can read it fifty times.

“Use a second agent.” Shared training and context can mean shared blind spots. I can’t assume the errors are independent. Two smoke alarms feel safer than one until you find out they’re on the same fuse.

“Use a model from a different vendor.” This can help. A different model may catch things the first missed. But a different vendor doesn’t guarantee independent errors: models can share training material, and here they’re reading the same context. And it still doesn’t solve the £100 case. The reviewer reads the same ambiguous spec and has to guess too, because neither model can see what I meant. Now I’m settling their disagreements by reading, which is the time I was trying to save.

“Tests will catch it.” Tests matter a lot, but tests are code too. Somebody still has to know whether a test captures what was actually intended. I started with four hundred unread lines. Now I have six hundred.

Who checks the code? The tests. Who checks the tests? More tests, written by whom? You keep stacking layers until you reach something the author didn’t make.

Pin the behavior before you touch it

The regress stops when you compare against something the author didn’t create. For changes to existing code, the obvious candidate is the existing code.

One tool I ended up building for this is a behavior pin. Before an agent rewrites anything, you write a characterization harness: tests that record what the current code actually does. Then you run them against two trees, the old one and the new one.

Say I have a pricing function using that strictly-over-£100 rule, with a quirk I don’t know about. Exactly £100.00 gets no discount. Above the threshold, it rounds the discount down to the nearest penny, so £100.01 gets £10.00 off, but £109.99 gets £10.99 rather than £11.00. I want an agent to tidy the function up without changing what it does.

First I pin the existing function:

discount(99.99)  == 0.00
discount(100.00) == 0.00
discount(100.01) == 10.00
discount(109.99) == 10.99   // this case captures the rounding quirk

I run those against the old tree, the code as it sits in git right now, which the agent can’t negotiate with. They pass. That matters, because it means the harness describes behavior that exists rather than behavior I wish existed. I can’t change the old implementation to suit the tests. I can still write weak tests, though. The fixed tree gives me a reference; it doesn’t tell me which cases or observations I’ve missed.

Only then does the agent get to rewrite the function. Afterwards, I run the same assertions against the new tree. If discount(109.99) still returns 10.99, the quirk survived for that input. Green means the new version matches the old one on the behavior the harness checks, which can include details nobody remembered.

The order is what makes it work. An LLM may well write the tests, so their coverage and assertions still need judgment. But the harness exists before the new code does, and it’s been checked against an old tree that isn’t up for discussion. Without that ordering, you’ve got a student marking their own exam. A pin works because the answer key for those cases was sealed before the student walked in. I have to keep it sealed, rather than let the rewrite quietly change the tests too.

Two caveats.

A pin checks that the covered behavior is the same. It doesn’t prove the whole implementation is equivalent, or that the behavior is right. In the example, it kept the rounding quirk on the tested inputs, and if that quirk is a bug, the pin carries the bug forward. That’s deliberate when the job is to preserve behavior. But green only ever means “unchanged on what we checked.”

And brand-new code has no old tree to pin against. That particular reference is missing. You can use other references the author didn’t produce, like acceptance tests written by a person, a real upstream API, or recorded production traffic. All of them cost human time. That’s the price of having no previous version.

Every commit turns new code into old code, though, so from version two onwards, changes can be guarded by a reference you got almost for free. The catch runs the other way too. If an agent writes version one and you pin it, the £100 misunderstanding can become the behavior your tests preserve. The first version has no previous implementation to compare against, which is why it deserves more of my own reading time.

For a deliberate behavior change, somebody still has to approve which expectations change and why. I keep the unaffected behavior pinned and review the expected differences against the new requirement. A bug fix shouldn’t fail just because it stops reproducing the old bug, but changing a test to make the build green isn’t enough either.

Writing down what you mean

Now turn the same idea around. On Naur’s account, the theory can’t be fully captured in a spec any more than it can be recovered from code alone. That’s the strongest objection to everything I’ve said so far, and I agree with it.

But I’m not trying to capture intent whole. I’m trying to capture what it leaves behind. A decision record doesn’t say “here’s what we meant.” It says “we picked X over Y because of Z.” That’s something the theory produced rather than the theory itself, and it can be written down. Naur didn’t argue for writing nothing. He said documents are necessary and never enough.

“Can’t capture it completely” also isn’t the same as “can’t capture it usefully.” The alternative to an imperfect record isn’t a perfect one. It’s intent sitting in a Slack thread, or in the head of someone who leaves in March. Every handover between people loses something, whether it’s a conversation, a doc or the code itself. If that ruled things out, nobody would talk to each other.

The objection also cuts the other way. If intent only lives in heads, then an agent, which can’t see into anyone’s head, starts every session with none of it. Writing down what you can is the only way it will ever get any.

Sometimes there isn’t even one intent to capture. Product means one thing by “orders over £100,” engineering means another, and everyone thinks they agree because they’re using the same words. Writing the spec is what drags that into the open, usually as a review comment that starts “wait, I thought we meant…”. The disagreement was there all along. In that case the spec isn’t a lossy copy of an agreement that already existed. It’s where the agreement gets made.

The part a machine can’t check

Every check I’ve described compares one thing against another. Pins compare against the old tree. Tests compare against expected outputs. Where there’s an outside reference, a machine can do the comparing.

How would a machine check that a spec matches what I meant? What would it compare against? The only written record is the spec. If a better record existed, that would be the spec. The reference isn’t on paper. It’s in my head, and the only way to get at it is to ask me.

So I don’t think the human review between intent and spec is a stopgap until models improve. It’s where the missing reference lives, and a few things follow from that.

Specs have to stay live. The dream version of spec-driven development says you write the spec precisely enough and the agent compiles it. If that’s your model, the objection is fatal. A compiler only sees what’s on the page, so any assumption nobody wrote down quietly disappears, and you get the wrong thing built precisely with no questions asked. Someone who holds the theory reads the same spec and notices what’s missing: hang on, what about tax? A compiler can’t notice an absence. Keeping the spec live turns one lossy handover into several passes. It doesn’t need to be perfect on day one, it just needs enough passes for the gap to show.

Who reviews matters. Someone who holds the theory can say whether £100 was meant to exclude tax. A reviewer who wasn’t in the room may spot the ambiguity, but still needs someone to answer it.

An LLM can help here, but it can’t do this review alone. It can spot the gap (“including or excluding tax?”) because ambiguity is a property of the text. It can’t fill the gap, because the answer isn’t anywhere it can see. Its useful job is asking the questions and letting a person answer them. That’s real work, but it isn’t verification.

So what am I accountable for?

This is the question I dodged the first time I wrote this up. If I’m not reading every line, what am I actually standing behind?

My answer is the allocation. I’m accountable for which decisions got a person, which got a mechanical check, and why. If a pin let a regression through, the pin was mine. If an agent made an architectural call nobody looked at, the rule that let it through unexamined was mine. That’s narrower than “I read all of it,” but I can actually meet it, and it’s more honest than putting my name on diffs I skimmed.

Keeping my own theory

The other thing I skated over is that the human gate assumes a human who still holds the theory. If agents write most of the code, does my understanding slowly rot? I think it can, and I don’t have a tidy answer.

The things I think help are small. Write the spec and the decision records yourself instead of having an agent draft them, because writing them is how you keep the theory. Read the first version of anything new in full, since there’s no previous implementation to compare it against. And now and then, build a piece of the system by hand. It’s the quickest way I know to find out whether my picture of it is still true.

Which decisions get a pause

Nurses have a name for what happened to me after twenty approvals: alarm fatigue. Enough false alarms and the real one turns into background noise.

Agent setups rarely fail because nobody’s watching. They fail because the person watching is asked to approve forty low-stakes things and none of the high-stakes ones. Rubber-stamping isn’t a moral failing. It’s what you get when you ask someone to care about everything at once.

So which decisions should stop and wait for a person? The usual answer is “anything high-risk,” but risk turns into a matter of opinion fast. Ask two engineers and you’ll get two answers. A question people agree on more easily is: if this is wrong, what does undoing it cost? Cheap, let it go ahead. Expensive, stop.

The rule in my AGENTS.md reads:

Size the path by reversibility rather than effort: if this is wrong, what does undoing it cost? Cheap to undo - take the smaller path, even when the work is large. Expensive or impossible to undo - data loss, released contracts, security posture, anything others already depend on - take the High-Risk path, even when the diff is one line.

The decision that most needs surfacing is usually the one nobody noticed was being made.

Here’s one that got me. I was moving a UI and its backend-for-frontend onto a new API. I showed the agent the old BFF so it could see what it was replacing. Instead of tracing the downstream services and wiring the new BFF straight to them, it took a shortcut: the new API called the old one.

Everything resolved. Tests green, clean run. And it wasn’t a migration at all. I’d built a new layer in front of the layer that was supposed to be retired, and the old one was still doing all the work. Nothing failed, so nothing flagged it. I found it later, by reading.

I keep seeing the same pattern. The choice arrives as working code instead of as a question. Six months on, those choices are your architecture. Nobody made them in any accountable way, and there’s no “why” to dig up, because there was never a moment when anyone stopped and decided. There was a move that made sense locally, and then the agent carried on.

What I built, and what it doesn’t fix

Augmented Workflow is my attempt to give this work a shape that fits the problem. Where there’s an outside reference, it uses mechanical checks. Where the reference only exists in someone’s head, it makes the human judgment explicit and puts it where it’s needed.

It lives in the repo, so the guidance sits alongside the code an agent is working on. That doesn’t guarantee it’ll be read, but it makes it easier to find than a Slack thread, a meeting or the memory of whoever happened to be around last month. Two kinds of thing go in there.

The first kind keeps human judgment. A living spec says what the system is supposed to do now: requirements, acceptance criteria, constraints, edge cases, open questions. Decision records capture the moment a fork appeared. Local files or DynamoDB. The new API wired to downstream services, or wrapped around the old BFF. £100 with tax or without. Neither pretends to hold the whole theory. They keep what can be kept, so the next person or agent doesn’t have to guess the architecture from whatever code happened to get written.

The second kind compares one artifact against another. Pins compare a rewrite to the old tree. Trace checks that stated requirements link to tests and implementation. Freshness gates check process claims against recorded review markers. Workflow trace compares the path the agent took with the path the work required. None of these proves the work is good. A pin checks “same on the covered behavior.” Trace checks “linked.” A freshness gate checks that a recent review is recorded, not that the review happened as claimed or was any good. But each one compares two things instead of asking the system to mark its own homework.

Now the limits. AGENTS.md isn’t a contract. It’s still a prompt, and I can’t make an agent read it, understand it or follow it. Nobody has solved that. Cursor rules, Spec Kit, BMAD, repo instructions and my own rules all hit the same wall. So nothing that really matters can depend on the agent cooperating. The load-bearing parts have to be ordinary files and ordinary checks that you can inspect without trusting the agent’s account of what it did.

The gap I can’t close is decision surfacing. If an agent makes an architectural choice without noticing it was a choice, no script can reliably spot the missing decision record. Noticing that a judgment call happened is itself a judgment call. You can narrow the gap with path-based rules, like requiring a decision record whenever auth, billing, persistence, security posture or public contracts change. You can’t close it. That’s why the reversibility rule matters so much: the workflow can’t see every decision, so it needs a simple test for which ones get a person.

So

I caught the data store problem because I happened to read the file. That’s the exact habit I’ve spent this whole piece saying I can’t count on any more. The ones I didn’t catch are, by definition, in the files I didn’t read.

You’re not going to read all of it again. Arithmetic settled that some time last year. What’s still up to you is what you choose to read, and what watches the rest.

Naur said a program dies when the team holding its theory breaks up. We can now produce code without anyone building that theory in the first place. Everything above is my attempt to keep an accountable person involved: mechanical checks where there’s something to compare against, and a person paying attention where there never will be.
